# 需要修改的搜图问题

更新日期：2026-10-17  
适用范围：第一个入口「说一句那座城」的地点解析、真实图片检索、下载与生成交接。  
依据：当前工作区代码与上一轮本地复现，不把注释或旧文档中的目标当成已经实现的能力。  
状态：整改方案，尚未实施；本次只重整文档。

## 1. 结论与目标

当前已完成搜图流程的第一轮纠错，但仍存在有效图片被丢弃、地标误解析、用户确认信息丢失等问题。应先修正确性，再建设正式上线需要的素材交付保障。

目标是：用户确认的地点身份在后续流程中保持一致，返回的参考图确实可以使用，来源和处理模式明确。不能把生成出了图等同于搜到了正确地点的真实照片。

对于任意自然语言、任意地点，不承诺外部检索永远成功。对宣布支持的城市和地标，应建立已验证且获准留存的自有素材库，在自身服务正常时稳定交付；超出覆盖范围时明确确认、检索或缺素材状态。

产品方向已确定为实际切穿的镂空作品。搜图负责提供正确素材，材料连通与可切性由最终几何检查证明，详见[产品差异化与交互方案](正式上线产品差异化与生成后交互方案.md)。

## 2. 当前链路与已完成项

```text
用户文字
  → /api/place-parse：本地别名 / DeepSeek 解析
  → 有歧义时展示候选
  → /api/photo-search：按地标名或城市名搜 Wikidata
  → Commons imageinfo 获取图片信息
  → 前端取第一候选实体中的最多两张
  → /api/scene-photo：下载、解码、转 PNG、拼接
  → 模型转换 / 本地二值化
  → 排版与 SVG
```

搜图或转换失败时，仍会自动进入 `/api/scene` 文生图；结果页已标注 AI 想象创作，但切换前没有征求用户对创作模式的选择。

| 已实现变化 | 当前边界 |
| --- | --- |
| 搜图前有地点解析 | 解析的高置信判断和城市地标一致性仍有问题 |
| 去掉中文查询排除海外实体规则 | 不代表已经核验实体国家和行政归属 |
| 移除 P577，改用官方 imageinfo | 文件名映射存在丢图问题 |
| 候选附带 Wikidata 实体 ID | ID 代表搜索结果所属实体，尚未与用户确认地点可靠绑定 |
| 不再跨候选实体随机抽图 | 城市实体的多张图片仍可能包含不同建筑 |
| 下载后检查尺寸、解码并转 PNG | 体积限制和来源约束仍不完整，且未保存为稳定素材 |
| 结果页显示来源或 AI 想象创作 | 来源记录缺作者，实际用图与来源可能错配 |
| 主流程接口按 scope 隔离限流 | 当前仍是进程内限流，不是跨实例的账户配额 |

上述已完成项保留，不重复建设旧版修复。

- **P2：** 正确流程成立后扩展覆盖与排序。

## 4. P0：先修四个正确性问题

### S01：统一文件名和规范标题映射

**当前问题：** `fetchImageInfo` 从 `descriptionurl` 的 `File:` 后面取文件名作索引，后续却使用 Wikidata 原始文件名查询。空格、下划线和 URL 编码不同就匹配失败。

上一轮模拟响应复现：

```text
Wikidata：Eiffel Tower.jpg
Commons 来源页：File:Eiffel_Tower.jpg
官方响应有可用 thumburl，但最终返回 0 张候选。
```

**需要修改：**

- 读取 API 返回的页面规范标题，不通过来源 URL 猜文件名。
- 处理 API 的标题规范化映射与适用的重定向映射。
- 建立统一文件名比较规则，正确处理空格、下划线和百分号编码；不盲目把整个文件名转小写。
- 保留原始名、规范名与素材 ID，展示名称不承担唯一标识职责。

**验收：** 有效候选不会因空格、中文编码、规范标题变化而丢失；缺文件与确实无缩略图的情况有独立测试。

**不需要改生图 Prompt。**

### S02：修正地点解析与置信度

**已复现的当前结果：**

| 输入 | 当前错误或遗漏 |
| --- | --- |
| 我想念东京的歌剧院 | 解析为 Tokyo + Sydney Opera House，且高置信 |
| 巴黎的悉尼歌剧院 | 城市与地标冲突，却高置信 |
| London and Paris | 只取 Paris，且高置信 |
| 我想念巴黎圣母院 | 只识别巴黎，明确地标丢失 |
| Paris, Texas | 命中 Paris 后丢失 Texas，不进入消歧 |

**需要修改：**

- 本地索引返回所有合理匹配，不按遍历顺序直接取第一项。
- 英文匹配考虑词边界，地标匹配优先完整名称，避免短别名提前吞掉长名称。
- 「歌剧院」「铁塔」等泛称结合城市语境解释，不能无条件映射到唯一海外建筑。
- 显式地点冲突、多城市和行政区修饰优先于本地快速返回规则。
- 城市匹配成功但句子仍有未解析的明确地标时，继续解析或请用户补充，不能静默只搜城市。
- 地标库维护所属城市、国家及外部 ID；数据缺失时保留不确定性。
- LLM 输出严格校验。缺失或非法的 confidence 不默认 high；候选为空或格式损坏时正常降级，不让整个接口意外异常。
- Prompt 用于提取和解释，最终高置信需要规则与实体证据支持。

**验收：** 上表输入得到正确解析或明确确认请求；未核验的城市地标冲突不会直接进入自动生成。

### S03：确认后的身份必须贯穿任务

**当前问题：** 前端有国家和行政区候选，但搜索只传单个名称字符串。`pickCandidate` 丢掉原地标信息；`faithfulGenerate` 和失败兜底又使用原始输入推断地点。用户选择不能保证后续继续遵守。

**需要修改：**

1. 建立确认地点记录，至少包括内部 ID、外部实体 ID、城市、国家、行政区、用户明确地标与确认状态。
2. 搜索使用确认记录，名称只是检索别名，不替代身份。
3. 搜索结果核验所属地点；不能直接认为全局排序第一项就是用户选中的实体。
4. 生成任务绑定确认记录、选定地标和素材 ID。
5. 城市名排版使用确认后的标准城市字段，不重新从整句推断。
6. 重试保留该记录。切换到艺术创作也保留城市、地标约束，除非用户主动更换。

**验收：** 确认某个同名城市后，搜索、参考图、生成、城市名、重试都不跳回另一个城市；明确指定地标不会在候选选择中丢失。

**主要是数据契约与前后端修改，不是换一段 Prompt。**

### S04：同一实体不一定是同一建筑

**当前问题：** 输入只有城市时，搜索结果可能是城市实体，其主图、横幅和其他照片包含不同地标。前端按该实体 ID 取两张，后端只要下载到两张就拼接，没有验证互补视角或同一建筑。

**需要修改：**

- 用户指定建筑时，锁定该建筑实体，并检查城市归属。
- 只指定城市时，从该城市的已验证可用地标中选定一个，再选择参考图；支持用户换地标。
- 只有经记录或核验属于同一地标的图片才可作为多视角参考。
- 默认使用一张最佳主参考图，不为凑两张而拼接。
- 向图像模型明确传入目标建筑，而不是让它从城市照片中自行决定主体。

**验收：** 同城市不同建筑不作为同一建筑的两个视角；同地标参考图与最终主体可追溯。

## 5. P1：正式上线前补齐

### S05：受控下载与资源限制

当前接口接受任意 HTTP(S) URL，并只按 `Content-Length` 判断大小。缺失或不真实的响应头可绕过该限制；输入 URL 与重定向目标也缺少受控范围。

**修改方式：后端服务与素材契约。**

- 优先接收素材 ID，由服务端解析已验证来源，不信任前端任意地址。
- 约束目标协议、允许来源和重定向，阻止访问本机及内网目标。
- 流式读取并限制实际下载字节；同时限制解码像素与输出规模。
- 下载、解码、尺寸检查和必要存储成功后，才标记素材 ready。
- 各来源有限重试与独立超时，同时有总任务预算；生成阶段也受剩余预算约束。

**验收：** 无长度头的超大响应、非法目标、重定向到内网、损坏文件、超大像素图都被正确拒绝。

### S06：实际用图、许可与来源对应

当前只传第一候选的标题、来源页和许可字符串。第一张下载失败而第二张成功时，返回来源仍可能指向第一张；使用两张时也只记录一条。当前尚未取得作者等完整信息。

**修改方式：素材数据、后端与前端。**

- 每张候选使用稳定 assetId，并记录标题、作者、来源页、许可、原始 URL 和文件信息。
- 下载结果保留输入素材 ID，不把图片数组和来源记录分开处理。
- 返回实际参与转换的素材列表、主参考图和处理模式。
- 缺失作者或许可要求不明确时，不把图片自动纳入公开商用底库。
- 来源随作品、版本和导出保存，前端按需展示所有参与素材。

**验收：** 第一张失败、第二张成功，以及双图输入三种情形下，显示来源与实际用图完全一致。

### S07：明确失败状态和模式选择

当前异常和真实空结果容易合并为空候选；前端自动进入文生图。已增加结果页标注，但尚未做到用户可控制切换。

**修改方式：接口状态与交互。**

| 状态 | 处理 |
| --- | --- |
| needs_confirmation | 显示地点候选或要求补充 |
| place_not_found | 请求补充地点，不直接想象一个城市 |
| no_verified_photo | 提供上传、换参考目标，或明确选择艺术创作 |
| temporarily_unavailable | 复用自存素材或重试，不冒充真正无照片 |
| ready | 有已验证可交付素材，进入转换 |

保留 `photo_reference_model`、`photo_reference_local`、`imagination` 等清楚的处理模式，不根据 attribution 是否存在推断全部处理事实。

**验收：** 用户知道是否切换为想象创作；模型转换失败后仍能复用已选照片和地点，不重新随机选主体。

### S08：建立自有已验证素材库

**修改方式：地点数据、对象存储、审核与素材服务。**

- 支持列表细化到城市和具体地标；有城市素材不代表支持用户指定的所有建筑。
- 保存获准使用和留存的真实文件，保留来源、作者、许可与审核记录。
- 已覆盖地点优先命中底库；外部来源用于新增与补充。
- 素材健康检查失败时下架或替换，保留审核追溯。
- 不把未经授权的用户原图默认转为公共底库素材。

**验收：** 外部检索不可用时，已覆盖地标仍能从自有存储取得图片。存储和自身服务异常单独计入可用性，不能宣称绝不失败。

## 6. P2：扩展质量与覆盖

现有排序主要依据文件名是否像全景。后续增加主体完整度、遮挡、清晰度、视角与已有转换成功记录，身份正确始终是准入条件，不能用画质分数抵消错地点。

对镂空建筑优先选择外轮廓辨识度高、结构清楚的照片。正面图可以减少重构，但不把侧视图一律判错，也不在搜图阶段宣称最终可切。

先保留 Wikidata / Commons 来源，再根据部署地区可达性、使用条款、成本和真实召回表现评估一个正式图片搜索 API。不要把增加来源数量当作可靠性的替代。

## 7. 推荐的数据交接与实施顺序

```text
原始文字
  → ResolvedPlace：确认城市、地标、行政归属与身份依据
  → PhotoCandidate：候选资产、所属实体、来源元数据
  → VerifiedAsset：实际下载验证完成的文件与状态
  → GenerationTask：地点 + 地标 + 主参考图 + 辅助图 + 处理模式
  → DesignVersion：生成结果与实际使用的完整来源
```

实施顺序：

1. 修 S01 文件名映射，建立回归测试。
2. 修 S02 解析，同时设计 S03 身份契约。
3. 完成 S03 全链路传递与 S04 地标级参考图选择。
4. 完成 S05 下载边界、S06 来源与 S07 状态处理。
5. 建立 S08 首批已验证素材交付，随后扩展 S09。

不重复改造已完成的 P577、海外过滤和接口 scope 隔离；需要的是回归保护。

## 8. 测试与发布验收

上一轮检查中，现有 23 项单元测试与类型检查通过。但测试未覆盖新增地点解析、图片搜索和实景转换接口，不能据此认定检索链路已经通过验证。

必须补充：

- 文件名空格、下划线、中文编码、规范标题映射。
- 海外中文城市、同名城市、多城市、地标冲突、明确地标不丢失。
- 用户确认后的国家、行政区、地标在搜索与重试中保持一致。
- 同城市不同建筑不拼接，同地标多视角才可组合。
- 第一张下载失败、第二张成功时来源正确；双图来源完整。
- 下载与解码边界、空结果和服务故障分开。
- 无真实素材时不静默转为想象创作。
- 外站故障时，自有已覆盖素材仍可使用。

分别统计地点解析正确率、图片地点正确率、素材交付成功率、覆盖率、外部调用失败率与耗时。生成成功率单独统计，不把 AI 兜底算作真实照片检索成功。

## 9. 当前证据与限制

本次重整以当前代码与上一轮本地复现为依据，不重新宣称线上可达性或成功率已经验证。尚未完成生产部署网络测试、素材授权逐项审核或长时间服务稳定性测试。
